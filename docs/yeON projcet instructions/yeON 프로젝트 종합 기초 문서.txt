# yeON 프로젝트 종합 기초 문서

> **작성일**: 2026-05-11  
> **프로젝트**: yeON (경조사 통합 플랫폼 서비스)  
> **현재 상태**: 미완성 (핵심 로직 문제 + UI/UX 정적 문제)  
> **개발 도구**: Claude Code (프론트엔드) + Codex (백엔드)

---

## 1. 프로젝트 비전 및 현재 상태

### 1.1 프로젝트 정의

**yeON**은 결혼식과 장례식 등 주요 경조사의 전 과정을 하나의 플랫폼에서 통합 관리하는 서비스입니다. 현재 경조사 준비 과정에서 사용자가 겪는 핵심 문제는 다수의 업체를 개별적으로 탐색하고 비교해야 하는 정보 비대칭, 불투명한 추가 요금 구조, 그리고 일정/초대/금전 관리가 여러 채널로 분산되어 있다는 점입니다. yeON은 이 모든 과정을 **플랜 생성 → 업체 견적/상담 → 예약 확정 → 초대장 공유 → 금전 정산**이라는 단일 흐름으로 연결하여 사용자 편의와 신뢰를 동시에 확보합니다.

### 1.2 핵심 차별점

yeON이 기존 서비스와 구별되는 핵심 차별점은 **모듈형 투명 견적** 시스템입니다. 각 업체의 서비스를 포함/제외/추가비용으로 항목화하여 가격 비교의 신뢰성을 강화하고, 행사 준비의 전 과정을 단절 없이 연결합니다. 또한 비대면 송금과 오프라인 데이터 업로드를 통합한 정산 시스템은 기존에 수작업으로 처리하던 축의금/부의금 관리를 자동화합니다.

### 1.3 현재 진행 상태 및 블로커 분석

| 항목 | 상태 | 상세 |
|---|---|---|
| 프로젝트 설정 (Next.js 14, Prisma, Tailwind) | 완료 | `npm run build` 성공 확인 |
| 라우팅 구조 (웨딩/장례 분리) | 완료 | App Router 기반, 역할별 리다이렉트 |
| 인증 시스템 (NextAuth JWT) | 완료 | 데모 계정 3개 동작 |
| 핵심 워크스페이스 UI (4단계 스테퍼) | 부분 완료 | 1009줄, 기본 폼 구현 |
| **핵심 비즈니스 로직 (견적/예약 상태 관리)** | **미완성** | **블로커 #1: 상태 전이 로직 부재** |
| **모듈형 가격 견적 시스템** | **설계 중** | **블로커 #2: 모듈화 구조 미확정** |
| **UI/UX 인터랙션 (애니메이션, 감성 피드백)** | **미완성** | **블로커 #3: 정적이고 폼 위주** |
| 정산 시스템 (송금/엑셀 업로드) | 미착수 | 기능 명세만 존재 |
| 모바일 초대장/부고장 | 미착수 | 기능 명세만 존재 |

현재 프로젝트가 진행되지 못하는 근본 원인은 세 가지입니다. 첫째, Prisma Schema가 불완전하여 데이터가 정상적으로 흐르지 않습니다. 둘째, 업체의 가격 모듈화 구조가 확정되지 않아 견적 시스템을 구현할 수 없습니다. 셋째, UI가 단순한 폼 나열에 그쳐 사용자가 서비스에 몰입하지 못합니다.

## 2. 시스템 아키텍처

### 2.1 기술 스택

| 분류 | 기술 | 버전 | 역할 |
|---|---|---|---|
| 프레임워크 | Next.js (App Router) | 14.2.x | 풀스택 React 프레임워크 |
| 언어 | TypeScript | 5.7.x | 정적 타입 시스템 (Strict Mode) |
| UI 라이브러리 | shadcn/ui + Tailwind CSS | 3.4.x | 컴포넌트 + 유틸리티 CSS |
| 애니메이션 | Framer Motion (신규 도입) | 11.x | 마이크로 인터랙션 및 레이아웃 애니메이션 |
| 아이콘 | Lucide React | 0.511.x | SVG 아이콘 시스템 |
| ORM | Prisma | 7.7.x | 타입 세이프 데이터베이스 접근 |
| 데이터베이스 | SQLite (better-sqlite3) | - | 로컬 파일 기반 RDBMS |
| 인증 | NextAuth.js | 4.24.x | JWT 기반 세션 관리 |
| 폼 관리 | React Hook Form + Zod (신규 도입) | - | 선언적 폼 검증 |

### 3.2 엔티티 상세

아래는 기능 명세서를 기반으로 도출한 핵심 데이터 모델입니다. 특히 모듈형 가격 견적을 지원하기 위한 JSON 구조가 포함되어 있습니다.

**User (사용자)**: 시스템의 모든 사용자를 하나의 테이블에서 `role` 필드로 구분합니다.

| 필드 | 타입 | 설명 |
|---|---|---|
| id | String (cuid) | 고유 식별자 |
| email | String (unique) | 로그인 이메일 |
| password | String | bcrypt 해시 비밀번호 |
| name | String | 사용자 이름 |
| phone | String? | 연락처 |
| role | String (USER/VENDOR/ADMIN) | 사용자 역할 |

**VendorProfile (업체 프로필)**: 업체 사용자의 추가 정보 및 승인 상태를 관리합니다.

| 필드 | 타입 | 설명 |
|---|---|---|
| id | String (cuid) | 고유 식별자 |
| userId | String (FK) | 연결된 사용자 |
| businessNumber | String | 사업자 등록번호 |
| companyName | String | 업체명 |
| category | String | 업종 카테고리 |
| status | String (PENDING/APPROVED/REJECTED) | 승인 상태 |

**EventPlan (행사 플랜)**: 모든 견적, 예약, 정산, 초대장이 연결되는 중심 엔티티입니다.

| 필드 | 타입 | 설명 |
|---|---|---|
| id | String (cuid) | 고유 식별자 |
| userId | String (FK) | 플랜 소유자 |
| eventType | String (WEDDING/FUNERAL) | 행사 유형 |
| title | String? | 행사명 |
| eventDate | DateTime? | 행사 예정일 |
| location | String? | 행사 지역 |
| guestCount | Int? | 예상 인원 |
| budget | Int? | 예산 (원) |
| status | String (DRAFT/ACTIVE/COMPLETED) | 플랜 상태 |

**VendorServiceModule (업체 서비스 모듈)**: 모듈형 가격 견적의 핵심 테이블입니다. 업체가 제공하는 개별 서비스 항목을 독립적인 모듈로 관리합니다.

| 필드 | 타입 | 설명 |
|---|---|---|
| id | String (cuid) | 고유 식별자 |
| vendorId | String (FK) | 소속 업체 |
| name | String | 모듈명 (예: "본식 스냅 2인") |
| category | String | 카테고리 (PHOTO/DECORATION/CATERING 등) |
| price | Int | 가격 (원) |
| description | String? | 상세 설명 |
| isBaseIncluded | Boolean | 기본 패키지 포함 여부 |

**QuoteRequest (견적 요청)**: 사용자가 업체에 보내는 견적 요청입니다.

| 필드 | 타입 | 설명 |
|---|---|---|
| id | String (cuid) | 고유 식별자 |
| planId | String (FK) | 연결된 행사 플랜 |
| vendorId | String (FK) | 대상 업체 |
| requirements | String | 요구사항 상세 |
| selectedModuleIds | String | 사용자가 선택한 모듈 ID 목록 (JSON) |
| status | String (PENDING/RESPONDED/ACCEPTED/CANCELED) | 요청 상태 |

**QuoteResponse (견적 응답)**: 업체의 모듈형 견적 응답입니다.

| 필드 | 타입 | 설명 |

### 4.2 견적 요청 상태 전이 규칙

yeON의 핵심 비즈니스 로직은 **상태 머신(State Machine)** 패턴으로 구현해야 합니다. 각 엔티티의 `status` 필드가 허용된 전이만 수행하도록 강제하는 것이 핵심이며, 이를 통해 잘못된 상태 변경으로 인한 데이터 불일치를 원천적으로 방지합니다.

| 현재 상태 | 허용 전이 | 트리거 주체 | 부수 효과 |
|---|---|---|---|
| PENDING | RESPONDED | 업체 | 사용자에게 알림 발송, 견적 응답 레코드 생성 |
| PENDING | CANCELED | 사용자 | 업체에게 알림 발송 |
| RESPONDED | ACCEPTED | 사용자 | 예약 신청 가능 상태로 전환 |
| RESPONDED | CANCELED | 사용자 | 종료 |

### 4.3 예약 상태 전이 규칙

| 현재 상태 | 허용 전이 | 트리거 주체 | 부수 효과 |
|---|---|---|---|
| PENDING | CONFIRMED | 업체 | 양측 알림, 캘린더 반영, 감성적 축하/위로 피드백 |
| PENDING | REJECTED | 업체 | 사용자에게 거절 사유 통지 |
| CONFIRMED | CHANGED | 사용자 | 업체 승인 대기 |
| CONFIRMED | CANCELED | 사용자 | 환불 규정 적용, 양측 알림 |
| CHANGED | CONFIRMED | 업체 | 변경 승인, 양측 알림 |

### 4.4 구현 코드 (lib/state-machine.ts)

```typescript
// lib/state-machine.ts
// 이 파일은 Codex가 구현합니다.

export type QuoteStatus = 'PENDING' | 'RESPONDED' | 'ACCEPTED' | 'CANCELED';
export type ReservationStatus = 'PENDING' | 'CONFIRMED' | 'REJECTED' | 'CHANGED' | 'CANCELED';

const QUOTE_TRANSITIONS: Record<QuoteStatus, QuoteStatus[]> = {
  PENDING:   ['RESPONDED', 'CANCELED'],
  RESPONDED: ['ACCEPTED', 'CANCELED'],
  ACCEPTED:  [],
  CANCELED:  [],
};

const RESERVATION_TRANSITIONS: Record<ReservationStatus, ReservationStatus[]> = {
  PENDING:   ['CONFIRMED', 'REJECTED'],
  CONFIRMED: ['CHANGED', 'CANCELED'],
  REJECTED:  [],
  CHANGED:   ['CONFIRMED'],
  CANCELED:  [],
};

export function canTransitionQuote(current: QuoteStatus, next: QuoteStatus): boolean {
  return QUOTE_TRANSITIONS[current]?.includes(next) ?? false;
}

export function canTransitionReservation(current: ReservationStatus, next: ReservationStatus): boolean {
  return RESERVATION_TRANSITIONS[current]?.includes(next) ?? false;
}

export class InvalidTransitionError extends Error {
  constructor(entity: string, from: string, to: string) {
    super(`[${entity}] 상태 전이 불가: ${from} → ${to}`);
    this.name = 'InvalidTransitionError';
  }
}
```

### 5.2 일반 사용자 여정 상세

아래 표는 일반 사용자(예비부부/유가족)가 yeON을 이용하는 전체 과정에서 겪는 페인포인트와 이를 해결하기 위한 구체적인 UX 개선 방안을 정리한 것입니다.

| **8. 초대장** | 템플릿 선택 후 편집/공유 | 편집 자유도 낮음, 미리보기 부족 | 실시간 미리보기 + 드래그 편집, 카카오톡/SMS 원클릭 공유 |


### 6.5 프론트엔드 컴포넌트 상세 (Claude Code 담당)

**ModularQuoteBuilder** (사용자 화면): 좌측에는 카테고리별로 그룹화된 모듈 타일(Tile) 그리드가 배치되고, 우측에는 현재까지의 선택 내역과 총액이 실시간으로 업데이트되는 Sticky Summary 패널이 배치됩니다. 모듈 타일을 클릭하면 선택 상태가 토글되며, Framer Motion의 `AnimatePresence`와 `layout` prop을 활용하여 요약 패널의 항목이 부드럽게 추가/제거됩니다. 총액 표시부에는 숫자가 굴러가듯 변경되는 카운트업(Count-up) 애니메이션을 적용합니다.

**VendorQuoteEditor** (업체 화면): 업체가 미리 정의해둔 패키지 프리셋을 원클릭으로 불러올 수 있는 드롭다운을 상단에 배치합니다. 제공 가능한 모듈 목록에서 고객 견적서 영역으로 모듈을 드래그하여 직관적으로 견적을 구성할 수 있도록 지원합니다.

**QuoteComparison** (견적 비교 화면): 여러 업체의 견적 응답을 나란히 배치하여 항목별(기본/추가/제외)로 비교할 수 있는 테이블 컴포넌트입니다. 가격 차이가 큰 항목은 하이라이트 처리하여 사용자의 의사결정을 돕습니다.

### 6.6 백엔드 로직 상세 (Codex 담당)

**calculateQuoteTotal**: 클라이언트에서 전송된 모듈 목록의 가격을 서버 측에서 재계산하여 가격 조작을 방지합니다. 각 모듈 ID에 대해 데이터베이스에서 실제 가격을 조회하고, 기본 패키지 가격과 선택된 옵션 가격을 합산합니다.

**submitQuoteResponse**: 업체가 작성한 모듈형 견적 데이터를 JSON 형태로 직렬화하여 `QuoteResponse` 테이블에 저장하고, 해당 견적 요청의 상태를 `RESPONDED`로 변경합니다. 이때 상태 머신 유틸리티를 통해 전이 가능 여부를 먼저 검증합니다.

## 7. UX 및 인터랙션 설계 가이드

### 7.1 핵심 디자인 원칙

**점진적 공개 (Progressive Disclosure)**: 복잡한 폼을 한 번에 보여주지 않고, 사용자의 선택에 따라 다음 질문이나 옵션이 부드럽게 나타나도록 설계합니다. 예를 들어, 플랜 생성 시 "어떤 행사를 준비하시나요?"라는 질문 하나로 시작하고, 선택에 따라 후속 질문이 자연스럽게 이어집니다.

**감성적 피드백 (Emotional Feedback)**: 성공, 실패, 대기 상태에 대해 명확하고 감성적인 애니메이션 피드백을 제공합니다. 웨딩 예약 확정 시에는 파스텔 톤의 Confetti 파티클이 화면에 뿌려지고, 장례 예약 확정 시에는 은은한 체크마크가 그려지며 "준비가 잘 진행되고 있습니다"라는 위로의 메시지가 표시됩니다.

**상황 인식형 UI (Context-Aware UI)**: 사용자가 선택한 행사 유형에 따라 전체 인터페이스의 분위기가 완전히 달라져야 합니다.

**장례 플랜 생성 마법사 (4단계)**

### 8.2 협업 워크플로우 (5단계)

**Step 0 — 인터페이스 합의 (사전 작업)**

두 에이전트가 작업을 시작하기 전, 데이터 교환을 위한 TypeScript 타입과 API 응답 구조를 먼저 합의하고 `types/` 디렉토리에 정의합니다. 이 단계가 없으면 프론트엔드와 백엔드의 데이터 구조가 불일치하여 통합 시 대규모 수정이 필요해집니다.

```typescript
// types/quote.ts — 두 에이전트가 공유하는 인터페이스
export interface QuoteModule {
  id: string;
  name: string;
  category: string;
  price: number;
  isSelected?: boolean;
}

export interface QuoteResponseData {
  basePackage: { name: string; price: number; description: string };
  includedModules: QuoteModule[];
  optionalModules: QuoteModule[];
  excludedModules: { id: string; name: string; reason: string }[];
  totalPrice: number;
}

export interface QuoteRequestPayload {
  planId: string;
  vendorId: string;
  requirements: string;
  selectedModuleIds: string[];
}
```

**Step 1 — 병렬 개발 (Codex: 백엔드 / Claude Code: 프론트엔드)**

Codex는 Prisma Schema 작성, 마이그레이션, Server Actions 구현, Seed 데이터 생성을 순차적으로 진행합니다. 동시에 Claude Code는 정의된 타입을 바탕으로 Mock 데이터를 사용하여 UI 컴포넌트를 개발합니다. 이 단계에서 두 에이전트는 서로 다른 Git 브랜치에서 작업하여 충돌을 방지합니다.

**Step 2 — 통합 (Integration)**

백엔드 API가 준비되면, Claude Code가 Mock 데이터를 실제 Server Actions 호출로 교체합니다. 이 과정에서 API 응답 지연 시의 스켈레톤 UI 처리는 Claude Code가, 에러 응답 구조와 핸들링 로직은 Codex가 주도합니다.

**Step 3 — 검증**

`npx tsc --noEmit` (타입 에러 0), `npm run lint` (경고 0), `npm run build` (성공) 세 가지를 모두 통과해야 합니다.

**Step 4 — 핸드오프 기록**

한 에이전트의 작업이 완료되면, 커밋 메시지 또는 `STATUS.md`에 상대 에이전트가 참고할 수 있는 요약 정보를 남깁니다.

### 8.3 AGENTS.md 업데이트 권장안

현재 프로젝트의 `AGENTS.md`에 아래 내용을 추가하여 두 에이전트가 컨텍스트를 공유할 수 있도록 합니다.

```markdown
## Agent roles
- **Claude Code**: Frontend specialist. Owns `app/`, `components/`, `hooks/`, CSS.
- **Codex**: Backend specialist. Owns `prisma/`, `app/actions/`, `lib/`, `types/`.

## Shared contracts
- All shared TypeScript interfaces live in `types/`.
- Both agents MUST import types from `types/` — never define inline.

## Integration protocol
- Frontend uses mock data until backend APIs are ready.
- Backend commits include a summary of available endpoints in STATUS.md.
- After integration, both agents verify: `tsc --noEmit && lint && build`.

## New dependencies
- framer-motion (animation)
- react-hook-form + @hookform/resolvers + zod (form validation)
```

| 4.1 정산 시스템 백엔드 | Codex | 엑셀 파싱, 통계 집계 API | `app/actions/transaction.ts` |
| 4.2 정산 시스템 프론트엔드 | Claude Code | 드래그 앤 드롭 업로드, 차트, 다운로드 | 정산 관련 컴포넌트 |
| 4.3 모바일 초대장 | 협업 | 템플릿 편집기 + 동적 라우팅 공유 페이지 | `app/invitation/[id]/` |
| 4.4 알림 시스템 | Codex | 상태 변경 시 인앱 알림 | `app/actions/notification.ts` |

### Phase 5: 프로덕션 준비 (1~2주)

| Task | 담당 | 상세 | 산출물 |
|---|---|---|---|
| 5.1 DB 전환 | Codex | SQLite → PostgreSQL 마이그레이션 | 수정된 schema + 환경변수 |
| 5.2 배포 환경 | 협업 | Vercel 또는 자체 서버 배포 설정 | 배포 스크립트 |
| 5.3 보안 강화 | Codex | 입력 검증, CSRF, Rate Limiting | 미들웨어 |
| 5.4 성능 최적화 | Claude Code | 이미지 최적화, 코드 스플리팅, 번들 분석 | 최적화된 빌드 |

## 10. 즉시 적용 가능한 Prisma Schema

```prisma
generator client {
  provider = "prisma-client-js"
}

datasource db {
  provider = "sqlite"
  url      = env("DATABASE_URL")
}

// ─── 사용자 및 인증 ───────────────────────────────────

model User {
  id            String         @id @default(cuid())
  email         String         @unique
  password      String
  name          String
  phone         String?
  role          String         @default("USER")
  createdAt     DateTime       @default(now())
  updatedAt     DateTime       @updatedAt

  vendorProfile VendorProfile?
  eventPlans    EventPlan[]
  quoteRequests QuoteRequest[]
}

model VendorProfile {
  id             String              @id @default(cuid())
  userId         String              @unique
  businessNumber String
  companyName    String
  category       String
  description    String?
  location       String?
  status         String              @default("PENDING")
  createdAt      DateTime            @default(now())

  user           User                @relation(fields: [userId], references: [id])
  serviceModules VendorServiceModule[]
  quoteResponses QuoteResponse[]
  reservations   Reservation[]
}

// ─── 업체 서비스 모듈 (모듈형 가격 견적의 핵심) ──────

model VendorServiceModule {
  id             String        @id @default(cuid())
  vendorId       String
  name           String
  category       String
  price          Int
  description    String?
  isBaseIncluded Boolean       @default(false)
  isActive       Boolean       @default(true)
  sortOrder      Int           @default(0)
  createdAt      DateTime      @default(now())

  vendor         VendorProfile @relation(fields: [vendorId], references: [id])
}

// ─── 행사 플랜 ────────────────────────────────────────

model EventPlan {
  id            String         @id @default(cuid())
  userId        String
  eventType     String
  title         String?
  eventDate     DateTime?
  location      String?
  guestCount    Int?
  budget        Int?
  status        String         @default("DRAFT")
  createdAt     DateTime       @default(now())
  updatedAt     DateTime       @updatedAt

  user          User           @relation(fields: [userId], references: [id])
  quoteRequests QuoteRequest[]
  reservations  Reservation[]
  transactions  Transaction[]
  invitation    Invitation?
}

// ─── 견적 요청/응답 ───────────────────────────────────

model QuoteRequest {
  id              String          @id @default(cuid())
  planId          String
  vendorId        String
  requirements    String
  selectedModules String          @default("[]")
  preferredDate   DateTime?
  budget          Int?
  status          String          @default("PENDING")
  createdAt       DateTime        @default(now())

  plan            EventPlan       @relation(fields: [planId], references: [id])
  user            User            @relation(fields: [vendorId], references: [id])
  responses       QuoteResponse[]
}

model QuoteResponse {
  id          String        @id @default(cuid())
  requestId   String
  vendorId    String
  basePrice   Int
  modules     String        @default("{}")
  totalPrice  Int
  note        String?
  createdAt   DateTime      @default(now())

  request     QuoteRequest  @relation(fields: [requestId], references: [id])
  vendor      VendorProfile @relation(fields: [vendorId], references: [id])
  reservation Reservation?
}

// ─── 예약 ─────────────────────────────────────────────

model Reservation {
  id              String         @id @default(cuid())
  planId          String
  vendorId        String
  quoteResponseId String?        @unique
  reservedDate    DateTime
  totalAmount     Int
  status          String         @default("PENDING")
  createdAt       DateTime       @default(now())
  updatedAt       DateTime       @updatedAt

  plan            EventPlan      @relation(fields: [planId], references: [id])
  vendor          VendorProfile  @relation(fields: [vendorId], references: [id])
  quoteResponse   QuoteResponse? @relation(fields: [quoteResponseId], references: [id])
}

// ─── 정산 ─────────────────────────────────────────────

model Transaction {
  id         String    @id @default(cuid())
  planId     String
  senderName String
  amount     Int
  relation   String?
  message    String?
  type       String    @default("OFFLINE")
  createdAt  DateTime  @default(now())

  plan       EventPlan @relation(fields: [planId], references: [id])
}

// ─── 초대장 ───────────────────────────────────────────

model Invitation {
  id          String    @id @default(cuid())
  planId      String    @unique
  templateId  String
  shareUrl    String    @unique
  content     String    @default("{}")
  isPublished Boolean   @default(false)
  createdAt   DateTime  @default(now())
  updatedAt   DateTime  @updatedAt

  plan        EventPlan @relation(fields: [planId], references: [id])
}
```
